# PC画面の鮮明さ：参照との比較

2026-09-10。参照は [My Room in 3D](https://github.com/brunosimon/my-room-in-3d/tree/5d00b3f870da81f103e901e0d12e20bbcc816834) の公開ソース・同梱動画、現行は本プロジェクトのソースとベイク済みGLBを読み取り調査した。動画メタデータは `ffprobe`、投影サイズは Three.js によるオフライン計算。以下の1〜4節は素材・描画設定の変更前にまとめた調査。調査後の実装、実画素検証、フィルター比較の結果は5節に記載した。本プロジェクトへのリンクは現在の同名ファイルを指し、「調査時L」の行番号は当時の記録を残している。

## 結論

主因と考えられるのは、**描いている画面の本物らしさ、文字の表示サイズ、途中の縮小処理**。参照の動画は512×256で、現行の各PC画面より小さい。VideoTextureに置き換えたり、全画面を一律4Kにしたりするだけでは、素材の精巧さや見かけの文字サイズは改善しない。

現行には修正候補が二種類ある。Ghidra本文の中間縮小は描画処理の改善対象。小さすぎるUI文字・代用アイコン・画面全体を収める構図は、画面素材と見せ方の設計対象になる。拡大表示したMouse/Macには、追加のテクスチャ解像度が効く余地もある。

### 通常表示と拡大表示の画素予算

計算条件は描画領域1440×900、通常表示の初期カメラ・ズーム1、拡大表示は現行Inspectorのポーズ。GLBの実頂点・UVを投影した。外接矩形には画面外へはみ出した部分も含む。文字は代表位置での名目フォントサイズの投影値で、文字のインク部分の実測高さではない。DPR2は比較用の仮定で、利用中のブラウザの現在値を測定したものではない。

| Dell：Ghidra本文 | 1284×360 | 4.88 | 1337×376 | 5.02 |
| Mouse：プロセス一覧本文 | 676×390 | 3.40 | 1200×675 | 7.50 |
| Mac：メニューバー | 434×284 | 4.69 | 1039×675 | 11.50 |

DPR2なら文字のdevice pixel換算はこの約2倍だが、見かけの文字サイズは増えない。Dellは通常から画面幅を大きく使っており、Inspectorでも超横長画面全体を収めるため本文は約5 CSS pxのまま。全文を収めたままテクスチャだけ増やしても、読みやすい文字サイズにはならない。[通常カメラ（調査時L3）](../assets/js/screen-view.js) / [Inspectorのフィット計算（調査時L32）](../assets/js/device-focus.js)

InspectorをDPR2で描く場合、Dellの外接矩形は約2675×752 device pxで元素材にほぼ近い。一方、Mouseは約2400×1350に1536×864を貼るため線形約1.56倍、Macは約2079×1350に1536×998を貼るため約1.35倍の拡大になる。この近接表示では解像度追加に根拠がある。通常表示や斜め画面の局所密度まで一律に不足すると断定する数値ではない。

縦長390×844では、Dell全体をInspectorへ収めると約362×102 CSS px、同本文は約1.36 CSS pxまで縮む。モバイルで本文まで見せるなら、アプリ単位の拡大・切り替えなど別の見せ方が必要になる。

## 3. 描画設定の差と、原因ではないもの

| 項目 | My Room in 3D | 現行 | 判断 |
| --- | --- | --- | --- |
| 画面素材 | VideoTexture | CanvasTexture | 種類自体で鮮明さは決まらない |
| 拡大フィルター | Linear | Linear | 同系統 |
| 縮小フィルター | Linear、mipmapなし | LinearMipmapLinear、mipmapあり | 差は実在。画質への寄与はA/B未検証 |
| 色空間 | 入出力sRGB | 入出力sRGB | 未指定による色ずれではない |
| 画面material | MeshBasicMaterial | MeshBasicMaterial、toneMapped:false | 現行のAgX・照明・AOがPC画面をぼかす経路ではない |
| DPR | 最大2 | 最大2 | 参照だけ高DPRではない |
| アンチエイリアス | 有効 | 有効 | 参照だけ特別な画面用AAではない |
| 後処理 | usePostprocess=false | 直接描画 | 参照の高品質化用ポスト処理を移植する話ではない |

参照のThree r130 VideoTextureはmin/magともLinear、generateMipmaps=falseが既定。[r130の一次ソース](https://github.com/mrdoob/three.js/blob/r130/src/textures/VideoTexture.js#L10-L14)。現行はCanvasTextureの既定を保持し、anisotropyは起動後に端末の最大値へ上書きする。[CanvasTexture既定値](https://github.com/mrdoob/three.js/blob/r186/src/textures/CanvasTexture.js#L20) / [mipmap生成既定値](https://github.com/mrdoob/three.js/blob/r186/src/textures/Texture.js#L257) / [現行DPR・色空間（調査時L31）](../assets/js/desk.js) / [anisotropy上書き（調査時L64）](../assets/js/desk.js) / [画面material（調査時L90）](../assets/js/desk.js)

[参照DPR](https://github.com/brunosimon/my-room-in-3d/blob/5d00b3f870da81f103e901e0d12e20bbcc816834/src/Experience/Experience.js#L75) / [参照renderer設定](https://github.com/brunosimon/my-room-in-3d/blob/5d00b3f870da81f103e901e0d12e20bbcc816834/src/Experience/Renderer.js#L30) / [後処理無効](https://github.com/brunosimon/my-room-in-3d/blob/5d00b3f870da81f103e901e0d12e20bbcc816834/src/Experience/Renderer.js#L19)

mipmapを切ると縮小時の線が強く見える可能性はあるが、細線のちらつきやモアレも増えうる。Nearestへの一律変更も文字を復元する処理ではない。静止・スクロール・斜め画角を同条件で比較して決める必要がある。動画の30fpsと現行の30fps更新も同程度で、フレームレート増加は静止文字の解像度を増やさない。[現行更新頻度（調査時L263）](../assets/js/computer-screens.js)

## 4. 改善案の優先順位

1. **画面素材と文字サイズを、実際に見せる大きさから作り直す。** 最も実物に近づけやすい素材は、必要なアプリを実際に並べたスクリーンショット・画面収録。拡大時のUIスケールを決めてから取得する。コードと数値の更新を細かく制御したい場合は、実UIに沿った高解像度HTML/CSSまたはCanvasを作り、主要本文の表示サイズを先に決める。HTMLも画像へ焼いて3Dに貼れば最終的にはテクスチャなので、HTML化だけで自動的に鮮明になるわけではない。現在の汎用アイコンや文字の置き方の近似は、解像度を増やすだけでは実物にならない。[現在の代用アイコン（調査時L19）](../assets/js/computer-screens.js)
2. **Ghidraの文字の中間縮小を外す。** 最終表示幅で直接描くか、キャッシュを最終ピクセル寸法で生成して等倍合成する。静止中の文字はピクセルに合う座標を使い、滑らかなスクロールとは分けて評価する。これは素材全面刷新前でも試せる、小さな処理修正。現状の本文の小ささ自体は別途解決が必要。
3. **必要な近接表示だけ解像度を増やし、フィルターはA/Bで判断する。** DPR2の1440×900 Inspectorなら、Mouseは少なくとも約2400×1350、Macは約2080×1350相当を覆う素材が目安。縦横比を保った適切な寸法へ丸める。Dellは先にアプリ単位の見せ方・文字サイズを直す。mipmap有無は同じ素材・同じカメラで比較し、鮮明さと動作時の安定性を両方確認する。

次の実験としては、Ghidraの同じ数行だけを「現行」「最終寸法へ直接描画」「直接描画＋文字を読みやすいサイズへ変更」の3つで比較するのが原因を切り分けやすい。その後、同じ素材でmipmapのA/Bを行う。これらは提案段階であり、今回の調査では実装・画質比較をしていない。参照動画・素材を公開用アセットへコピーする必要もない。


## 5. 実装した改善（同日・調査後）

- 標準カメラを5cm下げ、位置固定の視線操作を維持。Screen ViewとInspectorに0.8〜4倍のレンズズームとボタンを追加。
- Ghidraの文字を最終幅435論理pxへ直接描画。本文は旧縮小後8.63px相当から11.4pxへ。既存の文字画像の縮小・引き伸ばしで解像度を増やさない。
- Dellの二重Canvas合成を除去し、描画したTextureをそのままモデルへ使用。
- 初期素材はDell5120×1440、Mouse2560×1440、Mac3072×1996、iPad2048×1536。静止した視線・ズームの実表示寸法とDPRから必要な密度を求め、対象画面を再ラスタライズする。GPUの旧領域は解放し、再生時刻とTexture参照は維持。
- Canvas上限はGPUの最大辺長、12,288px、64MP。無制限ズームではなく0.8〜4倍に対応し、さらに大きい画面で上限を超える場合はタイル化が必要。壁紙やアバターなど既存のビットマップ原画に、解像度変更だけで新しい細部が増えるわけではない。
- macOS/Chrome/Edge/VS Code/Caido/Codexのローカルアプリアイコンをネイティブ素材から配置。アプリ本文は引き続きこのサイト用の描画で、実アプリの録画ではない。
- 画面の演出を30秒周期に統一。実時刻を示す置き時計と、操作時だけ変わるMacのNotes遷移は独立。Ghidra/Codexの同期、Caidoの選択、Windowsのcaret/値を同じ状態へつなぐ。

参照動画の先頭・末尾も追加で測定した。PortfolioはRGB平均絶対差0.192/255でほぼ一致する一方、Streamは40.252/255でコード画面とBlender画面の切り替えがある。両方とも `loop=true` だが、両方の映像が同じ状態へ戻るように編集されているわけではない。

実ブラウザーのCanvas全画素をSHA-256で比較し、Dell/Mouse/iPadとも5秒↔35秒、15秒↔45秒、30秒↔60秒が一致した。29.966秒→30秒のRGB平均差はDell/Mouseが0、iPadが0.0285/255。iPadの30秒→30.033秒は新着チャットの移動があり1.604/255。丸角や部分復元の境界に前フレームが残る問題も、この検証で見つけて全面復元へ修正した。これは指定した時刻の実画素検証であり、全900フレームの対比較や全端末の30fps保証ではない。検証コードと測定値は公開対象外の `.scene-build/screen-quality/` に保存。

フィルターも、同じ素材・15秒の固定フレーム・DPR2・同一カメラでA/Bを実施（通常視点1倍とDell Inspector2倍）。この静止比較では、mipmap無効化だけで読みやすさが明確に改善するとは判断できず、本体は現在の異方性＋trilinearを維持した。QAページは `.scene-build/screen-quality/filter.html`。Three r186ではLinearFilterに対する異方性設定を省略するため、比較ページには実効GPU異方性を揃える機能を持たせた。動作時のちらつきの優劣は数値計測していない。

## 6. 実画面の参考画像に合わせた再調整（2026-09-10）

Dell と Mouse の形状・UV は正常で、画面面積はそれぞれ 1198.08×336.96 mm（32:9）、345.4×194.3 mm（ほぼ16:9）だった。近距離の画面端に置いた Mouse が横へ伸びて見える原因を、GLB の実頂点を使って確認した。FOV だけを変更してもこの比率は変わらないため、カメラを12 cm後退し、縦画角を60°から50.5°へ調整した。高さ1.03 m、視線だけを変える操作、0.8〜4倍ズームは維持する。

1440×900の投影外接矩形で、Dell は1274×358から1336×376 CSS px、Mouse は692×366から634×348、MacBook は442×287から443×287へ変化する。Mouse の横縦比は1.894から1.823となり、物理比率1.778に近づいた。これらは同一サイズのブラウザーを仮定した幾何計算であり、画面上の印象を完全に数量化するものではない。カメラの投影・画面への見通しは `tests/screen-view.test.js` で確認する。

提供されたアプリ単体の画像から、Dell 内の本文は以前の約半分の論理サイズが妥当と判断した。元画像の文字・ウィンドウの比率を保った座標でUIを描き、拡大時には最終ピクセル密度へ直接ラスタライズする。Ghidra は白い Listing と Decompiler を左右に並べ、Edge が右上を占める。参考画像内の個人の会話やセッション値は公開用素材へ取り込まない。

Dock は Dell だけに表示し、指定順の26種類のアプリアイコン、2本の白い区切り線、3枚の最小化ウィンドウを描く。素材はインストール済みアプリの公開アイコン資源から取得した。Calendar はローカルの実月日を使い、画面のPause中でも日付の変更で再描画する。Activity Monitor は30秒周期の演出用グラフ。

YouTube の確認では、通常の `https://www.youtube.com/` は `X-Frame-Options: SAMEORIGIN` を返した。ページ全体を埋め込む構成は使えない。公式 [IFrame Player API](https://developers.google.com/youtube/iframe_api_reference) は動画部分を埋め込めるため、実動画を使う場合はiPadの画面へHTMLプレーヤーを配置し、周囲のUIと分ける。クロスオリジンのページや動画を無条件でCanvasへ写せるわけではない。現在のiPadは引き続き自作の30秒描画で、実動画への切替は動画URLと表示方針の選択後に行う。


新しい Dell の演出は、プロンプト入力、関数・変数名変更、Edge と Caido の履歴、Replay、RDP 内の通知と電卓、最終出力までを30秒へ同期した。終盤は電卓・通知を閉じ、ReplayとHistoryを消去し、新しいチャットを開いて初期状態へ戻る。全面クロスフェードは使わず、先頭も終端も同じ描画経路で描く。すべて Canvas の描画で、MCP接続やリクエスト送信、プログラム実行は行わない。

最終検証では19件のNodeテスト、記事本文・URLの確認、HTML-Prooferの31リンク確認に合格。Ghidra表示コードの整合性を修正した後も、関連3テストとproduction buildが合格した。ブラウザーでは通常表示、最大4倍のズームと視線移動、Pause、MacBookのNotes表示とEscapeでの復帰を確認し、警告・エラーはなかった。狭幅カメラのフレーミングは数値テストで確認したが、今回のブラウザーではviewport overrideが期待どおり反映されなかったため、390px幅の目視確認や実機での性能確認は完了扱いにしていない。

実Canvas画素は、プレーヤーの初回操作表示が消えた定常状態について、2・5・15・20・25・30秒の各フレームと30秒後を比較し、Dell・Mouse・iPadの全組でSHA-256が一致した。DellとMouseは末尾29.9667秒→0秒のRGB平均差が0。iPadは自然な動きが続くため同一フレームではなく、既存と同じ平均差0.0285/255。読み出し前にはChromiumのCanvas readbackを暖機した（最初のGPUからCPUへの切り替わりによる差を除く）。コードと結果は公開対象外の `.scene-build/screen-quality/qa.js` と `results.json` に保存した。
